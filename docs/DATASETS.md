# Datasets

What data this system runs on, what it *could* run on, and — stated plainly — the difference
between the two.

## Reading this document

Every quantitative claim carries a provenance tag. There are exactly three:

| Tag | Meaning |
|---|---|
| **(measured)** | Computed in this repository by executing code. Reproducible with the command given. |
| **(derived)** | Arithmetic on values in `rai/config.py` or `rai/schemas.py`. No external source. |
| **(published)** | Taken from the dataset's own documentation or paper. **Not verified locally.** |

`CLAUDE.md` forbids fabricating dataset statistics. Where two of our own research files
disagree about a figure, the disagreement is printed rather than silently resolved. Where a
count can only come from the download, it says so.

**Status vocabulary**, used identically in every block below:

- `not downloaded` — nothing of this dataset exists on disk.
- `fetchable` — no credential needed; a loader could pull it now over the Bash tool's network.
- `credential required` — needs an account/API key, so it is out of scope for a 24 h offline-capable build.
- `loader ready` — an adapter exists in `rai/ingest/` and has been executed at least once.
- `present` — bytes on disk under `data/`.

**Repository state at time of writing (measured, `ls -la data/*`, `wc -c rai/ingest/__init__.py`):**
`data/raw/`, `data/interim/`, `data/processed/`, `data/synthetic/` each contain only
`.gitkeep`. `rai/ingest/__init__.py` is 0 bytes. **No external dataset has been downloaded and
no adapter has been written.** Every "Tier 1" row below is therefore a *commitment*, not a
result.

## 2. The decision this table encodes

The honest one-paragraph version, which is also the answer to the hardest question a judge can
ask ("why is your primary dataset synthetic?"):

> A 5.5 GB unlabelled-for-our-purpose download cannot make detection lead time measurable
> inside 24 hours. The synthetic spine can, because every injected fault carries an exact
> `onset`, `detectable_from`, `end` and `is_equipment_fault` flag (`rai/schemas.py::InjectedEvent`).
> That turns *"we detect faults early"* from a claim into a number with a definition. The cost
> is that no result on synthetic data is evidence about real turbines, and we say so in every
> place a number is reported.

Both halves of that sentence matter. The second half is §6.

## 3. Dataset 0 — RAI physics simulator (PRIMARY)

**Name / location:** generated by `rai/sim/` into
`data/synthetic/telemetry/{asset_id}.parquet`, `data/synthetic/events.parquet`,
`data/synthetic/site_met.parquet`.
**Licence:** project-internal; no third-party terms attach.
**Cadence:** 10 min wind, 15 min solar (`settings.wind_interval_min`, `settings.solar_interval_min`).
**Span:** `settings.sim_days = 45` days, ending at the simulation end timestamp
(2026-07-30 → 2026-09-12 for the frozen demo window). Seed `settings.sim_seed = 20260912`.

**Expected volume (derived from `rai/config.py`, not yet confirmed against generated files):**

| Quantity | Value |
|---|---|
| Wind assets × rows each | 18 × 6 480 = 116 640 |
| Solar assets × rows each | 24 × 4 320 = 103 680 |
| Total telemetry rows | **220 320** |
| Wind columns | 18 (per the canonical schema) |
| Solar columns | 16 |

Reproduce: `./.venv/Scripts/python.exe -c "from rai.config import settings, FLEET; ..."` — the
exact command and its output are in `docs/checkpoints/07-docs-ml.md`.

**Signals:** exactly the canonical telemetry schema (see `CLAUDE.md` and the simulator's
checkpoint record). Monitored subsets that the residual engine must model are frozen in
`config.WIND_SIGNALS` (7 signals) and `config.SOLAR_SIGNALS` (7 signals).

**Ground truth:** `data/synthetic/events.parquet`, rows matching `InjectedEvent`. Twelve
scenarios are required by `docs/API_CONTRACT.md`:

| Scenario | Component | `is_equipment_fault` | Discrimination role |
|---|---|---|---|
| `gearbox_bearing_wear` | gearbox | true | equipment positive |
| `generator_overheating` | generator | true | equipment positive |
| `pitch_misalignment` | pitch_system | true | equipment positive |
| `yaw_misalignment` | yaw_system | true | equipment positive |
| `string_outage` | dc_string | true | equipment positive |
| `inverter_derate` | inverter | true | equipment positive |
| `soiling_accumulation` | soiling | false | service action, not a fault |
| `anemometer_drift` | anemometer | false | sensor fault → data QC, not drivetrain work |
| `sensor_freeze` | anemometer | false | sensor fault → data QC |
| `curtailment_window` | — | false | grid instruction, not a fault |
| `cloud_transient` | — | false | weather |
| `icing_event` | — | false | weather |

Six equipment / six non-equipment by design — that balance is what makes
`equipment_vs_environment_accuracy` (§ `docs/EVALUATION.md`) a meaningful number rather than a
prevalence artefact. **The authority is the `is_equipment_fault` column in `events.parquet`,
not this table**; `scripts/evaluate.py` must read the flag, never a hard-coded list.

**Preprocessing required:** none for schema conformance (it is generated in the canonical
schema). The modelling pipeline still applies the same curation it would apply to real SCADA —
status/`operating_state` filtering, physical-range filtering, clipping-window exclusion for
solar — because the simulator injects curtailment, sensor freeze and icing precisely so that
curation is exercised.

**Known limitations (the ones that matter):**

1. **It cannot validate the system.** A model fitted to a simulator and evaluated on the same
   simulator measures self-consistency. The generative process and the detector share
   assumptions (first-order thermal lag, a specific power-curve shape, additive Gaussian noise),
   so the detector is solving an easier problem than reality poses. **This is the top limitation
   of the entire project.**
2. Noise is simpler than SCADA noise: no communication dropouts of arbitrary length, no
   mid-series unit changes, no 0/360° angle wrapping pathologies, no min/max/std columns that
   disagree with the mean (all of which CARE documents in real data).
3. Faults are drawn from twelve scripted profiles. Real degradation is a long tail; a detector
   tuned on twelve shapes will over-fit those shapes.
4. Forty-five days is short. It contains no seasonal cycle, no annual degradation trend, and
   only ~12.4 asset-months of held-out test data (derived: 42 × 9 / 30.4375), which bounds how
   precisely a false-alarm rate can be estimated at all (see `docs/EVALUATION.md` §7).
5. Peer structure is synthetic: four peer groups (`kutch-row-a`, `kutch-row-b`,
   `charanka-block-1`, `charanka-block-2`) with no per-turbine coordinates in the frozen
   registry — every `Asset` at a site shares one latitude/longitude (measured, `rai/config.py`).
   Wake effects are therefore a row-level proxy, not geometry.

**Status:** the simulator is owned by another task; at time of writing `data/synthetic/`
contains only `.gitkeep` (measured). This document will be correct once that task lands; it
does not claim the data exists.

## 4. External datasets

### 4.1 CARE to Compare — the benchmark we are measured against

| Field | Value |
|---|---|
| Canonical URL | https://zenodo.org/records/10958775 (first release) · latest version https://zenodo.org/records/15846963 (v6, July 2025) |
| Paper | Gück, Roelofs, Faulstich et al., *"CARE to Compare: A real-world dataset for anomaly detection in wind turbine data"*, MDPI **Data** 9(12):138, 2024 · DOI `10.3390/data9120138` · arXiv:2404.10320 |
| Licence | **CC-BY-SA-4.0** (published) — share-alike: any redistributed derivative dataset inherits the licence |
| Cadence | 10-minute SCADA (published) |
| Size | single **5.5 GB** zip (published) |
| Scale | **95 datasets · 36 turbines · 3 farms · ~89 turbine-years** (published) |
| Labels | **45 datasets contain a labelled anomaly event leading to a fault; 50 are normal-behaviour** (published) |

**Signals:** 86 features on farm A (Portugal, onshore, 5 turbines, sourced from EDP), 257 on
farm B and 957 on farm C (both German offshore) (published). Per-timestamp turbine status
labels allow training data to be filtered to healthy operation. Event metadata carries a
free-text fault description (e.g. gearbox bearing damage, transformer cell over-temperature).

**Internal disagreement, printed rather than resolved:**
`Renewable_Asset_Intelligence_Research_Compendium.md` states *44 labelled / 51 normal*;
`Renewable_Asset_Intelligence_Build_Research_Compendium.md` and the task brief state *45 / 50*.
Nothing in this repo can adjudicate that. The loader must count the event files in the
downloaded manifest and write the measured value into
`docs/checkpoints/` before any result is reported against it.

**ROLE here: independent validation (primary), case-memory seed (secondary).** It is the only
dataset that can answer "does the detector work on real turbines?", and it ships its own metric
(the CARE score: Coverage, Accuracy, Reliability, Earliness) so a result is directly comparable
to published work. It is *not* our training corpus in this build.

**Preprocessing required:**
1. Unzip 5.5 GB; load per-turbine CSV lazily (pyarrow / chunked pandas) — never `glob` into RAM.
2. Map each farm's feature set onto the canonical schema. Farms have 86 / 257 / 957 columns with
   farm-specific names; this is a per-farm mapping table, not a rename.
3. Drop `Min`/`Max`/`Std` columns by default — the authors document these as unreliable in
   places (std > possible max, min > avg, all-zero columns). `Avg` is the trustworthy statistic.
4. Farm A pitch min/max/std suffers 0°≡360° wrapping — use sin/cos or discard.
5. Filter training rows by the per-timestamp status label (healthy only). For farm A the status
   is *derived from the EDP logbook*, so it is legitimate as a training filter and illegitimate
   as an evaluation label.
6. Version check: v5→v6 fixed an hPa/bar unit error on two sensors and relabelled some events.
   Pin the record ID in the loader.

**Known limitations:**
- Anonymised: no rated power, rotor diameter or hub height. A physics power curve or an IEC
  air-density correction cannot be computed without assumptions, so only the learned NBM half of
  our wind model transfers directly.
- Heterogeneous feature sets across the three farms make leave-one-farm-out a genuine domain
  shift — which is the point, but it means a single feature matrix does not exist.
- 5.5 GB download plus mapping work does not fit alongside the rest of a 24 h build.

**Why it shapes the architecture even unread:** the paper's own mini-benchmark reports
**Isolation Forest at CARE score 0.14, random baseline 0.50, autoencoder 0.66** (published).
That single result is the reason `docs/ML_PLAN.md` forbids Isolation Forest from firing an
alert on its own.

**Status:** `not downloaded`. No loader (`rai/ingest/` is empty, measured).

### 4.2 Kaggle two-plant Indian solar — the fastest real check

| Field | Value |
|---|---|
| Canonical URL | https://www.kaggle.com/datasets/anikannal/solar-power-generation-data |
| Licence | Kaggle page terms; **no explicit open licence recorded in our research files** — research use, verify before redistribution |
| Cadence | 15 minutes (published) — identical to our solar cadence |
| Span | ~34 days, two Indian plants (published) |
| Size | four CSVs (generation + weather per plant), single-digit MB (published) |

**Signals:** per-inverter `DC_POWER`, `AC_POWER`, `DAILY_YIELD`, `TOTAL_YIELD`; plant-level
`AMBIENT_TEMPERATURE`, `MODULE_TEMPERATURE`, `IRRADIATION`. Exact row counts and the inverter
count per plant must come from the loader; they are not asserted here.

**ROLE: independent validation for the solar residual and peer-comparison engines.** It is the
closest real analogue to Charanka Solar Park — Indian site, inverter-level granularity, 15-minute
cadence, plant-level weather only. If the solar NBM cannot produce sane residuals here, the
synthetic result means nothing.

**Preprocessing required:** parse the two distinct datetime formats used across the files; join
generation to weather on `DATE_TIME` + `PLANT_ID`; pivot to one frame per inverter
(`SOURCE_KEY` → `asset_id`); derive `performance_ratio` from DC power, plate capacity and
`IRRADIATION`; localise naive timestamps to IST then convert to UTC.

**Known limitations:**
- 34 days: no seasonality, no degradation trend, no annual soiling cycle.
- **One irradiance sensor per plant.** Every inverter's residual shares that sensor's error, so a
  sensor drift looks like a simultaneous fleet-wide fault — which is a useful test of the
  peer/environment logic and a fatal confound for naive per-inverter thresholds.
- Community-reported quirks: irradiance-sensor drift at plant 1, and a DC-power scale difference
  between the two plants (widely discussed on the dataset page; **verify with the loader, do not
  assume**).
- No fault labels of any kind. Usable for residual sanity, peer behaviour and false-alarm rate;
  useless for detection recall.

**Status:** `not downloaded`, `fetchable` only with Kaggle credentials (the API needs a token).

### 4.3 NASA POWER — environmental context

| Field | Value |
|---|---|
| Canonical URL | https://power.larc.nasa.gov/docs/services/api/temporal/hourly/ |
| Licence | US Government open data; free, **no API key**, citation requested |
| Cadence | hourly (also daily/monthly); meteorology from 1981, solar from 1984 (published) |
| Size | per-point JSON/CSV — kilobytes per site-year |
| Signals | 380+ parameters (published); we need `ALLSKY_SFC_SW_DWN`, `ALLSKY_SFC_SW_DNI`, `ALLSKY_SFC_SW_DIFF`, `T2M`, `WS10M`/`WS50M`, `RH2M`, `PS`, `PRECTOTCORR` |

**ROLE: environmental context.** Two concrete uses: (a) drive the simulator's weather from a real
Gujarat climatology for Kutch (23.25 N, 69.67 E) and Charanka (23.90 N, 71.20 E) instead of a
pure synthesis, which makes `site_met.parquet` defensible; (b) act as an independent irradiance
reference when a site pyranometer is suspect — the `sensor_health` branch of
`EnvironmentEvidence`.

**Preprocessing required:** hourly → 10/15-minute interpolation (linear for temperature/pressure,
clear-sky-index-preserving for irradiance); UTC alignment; unit conversion (POWER reports
irradiance in Wh/m²/h ≡ W/m² hourly mean).

**Known limitations:** it is a reanalysis/satellite product on a coarse grid (~0.5° × 0.625°),
so it has no site microclimature and **no sub-hourly structure** — interpolating it cannot
create the 40-minute cloud transient that scenario `cloud_transient` depends on. Near-real-time
products lag by days. Treat as climatology, not as a nowcast.

**Status:** `fetchable` (no key; the Bash tool has network). Not fetched. No loader.

### 4.4 Kelmarsh & Penmanshiel — cross-farm validation

| Field | Value |
|---|---|
| Canonical URL | Kelmarsh https://zenodo.org/records/5841834 · Penmanshiel https://zenodo.org/records/5946808 (2016–mid-2021), updated release record 16807304 (to end-2024) |
| Publisher | Cubico Sustainable Investments |
| Licence | **CC-BY-4.0** (published) |
| Cadence | 10-minute SCADA (published) |
| Scale | Kelmarsh 6 × Senvion MM92 (~12.3 MW); Penmanshiel 14 × Senvion MM82 (28.7 MW) (published) |

**Signals:** wind speed/direction, power, pitch, rotor speed, nacelle and drivetrain
temperatures, **plus status, alarm and event logs, downtime records and turbine metadata**
(rated power, rotor diameter, hub height) — the metadata CARE anonymises away.

**ROLE: cross-farm validation and the peer-comparison test bed.** Enough identical machines at
one site to make peer statistics real; 2.05 MW Senvion units are the same class as our 2.0 MW
fleet, so the physics power curve transfers with only a rating change. The alarm logs are the
only realistic source for testing alarm-fusion behaviour.

**Preprocessing:** column mapping to the canonical schema; join alarm/status logs onto the
10-minute grid by interval; exclude downtime and curtailment before NBM training.

**Known limitations:** status and alarm logs are **not** component-level confirmed failure
labels, so these farms measure false-alarm rate and NBM quality, not detection recall. UK
climate: icing yes, desert dust no — the soiling and dust-forecast logic has nothing to validate
against here.

**Status:** `not downloaded`.

### 4.5 EDP open data + failure logbook — case memory, not training

| Field | Value |
|---|---|
| Canonical URL | https://www.edp.com/en/innovation/open-data/data · most-cited mirror https://data.mendeley.com/datasets/zjxjnjp3xs |
| Licence | CC-BY-SA (published) |
| Cadence | 10-minute SCADA, 2016–2017 (published) |
| Scale | our two research files disagree: one says *4 of 16 turbines (32 MW)*, the other *5 onshore Portuguese turbines*. **Printed, not resolved.** |

**Signals:** standard 10-minute SCADA **plus a dated, component-specific failure logbook**
(gearbox, generator, transformer, hydraulic group) — one of very few public pairings of
continuous SCADA with human-confirmed failure dates. It is the raw source behind CARE farm A.

**ROLE: case memory (`HistoricalCase`), explicitly not training data.** The logbook holds on the
order of tens of confirmed failures across two years (exact count must be counted by the loader).
That is far too few to train a supervised failure classifier without overfitting, and saying
otherwise would be the single easiest claim for a judge to dismantle. It is, however, exactly the
right size to seed a case library: a handful of *real* pre-failure trajectories to retrieve
against, each with a known outcome.

**Preprocessing:** align logbook timestamps to the SCADA grid; define a pre-failure window per
event (the CARE convention: the anomaly period ends where the fault begins); extract the same
trajectory feature vector the kNN memory uses (`docs/ML_PLAN.md` §M8) so real and synthetic cases
live in one space. Tag every case with `HistoricalCase.source = "edp_logbook"` so the UI can
distinguish real from synthetic provenance — the schema defaults this field to
`"synthetic_case_library"` precisely so the difference is never lost.

**Known limitations:** two years, five turbines, one site, one OEM. Logbook entries are free
text with inconsistent component naming. No offshore, no solar.

**Status:** `not downloaded`.

### 4.6 NREL PVDAQ (OEDI) — future primary solar corpus

| Field | Value |
|---|---|
| Canonical URL | https://data.openei.org/submissions/4568 · DOI `10.25984/1846021` · bulk `s3://oedi-data-lake/pvdaq/` (`--no-sign-request`) |
| Licence | **CC-BY-4.0** (OEDI terms, published) |
| Cadence | per-system, 1–15 minutes (published) |
| Size | **~17 GB parquet lake / ~512 GB CSV** (published) — use parquet |
| Signals | system metadata + performance time series; many systems include plane-of-array irradiance, module and ambient temperature, wind speed, precipitation |

**ROLE: research-only in this build; the intended primary solar training corpus afterwards.**
Dozens of systems across climates make it the only public source that can support a *transferable*
solar NBM and climate-conditioned soiling priors.

**Preprocessing:** select systems by metadata (climate zone, technology, sensor completeness);
per-system schema normalisation; timezone handling per site; QC against NSRDB irradiance.

**Known limitations:** size dominates everything else in a 24 h build. Per-system schemas are
heterogeneous, data quality varies by system-year, and coverage is almost entirely US climates —
soiling behaviour in Colorado is not soiling behaviour in Patan district, Gujarat.

**Status:** `not downloaded`.

### 4.7 DKASC Alice Springs — soiling laboratory

| Field | Value |
|---|---|
| Canonical URL | https://dkasolarcentre.com.au/download?location=alice-springs |
| Licence | site download terms; attribution requested |
| Cadence | 5 minutes, from ~2008 (published) |
| Scale | dozens of side-by-side PV systems of different module/inverter technologies, each with co-located weather (published) |

**ROLE: research-only — soiling and rain-cleaning validation.** Identical weather across

mineralogy and rainfall pattern differ from Gujarat's.

**Status:** `not downloaded`.

### 4.8 SDWPF / KDD Cup 2022 — fleet scale with weather forecasts

### 4.9 CAMS / ERA5 / AERONET / MERRA-2 — enrichment

| Source | Gives | Access | Role |
|---|---|---|---|
| **CAMS global atmospheric composition forecasts** | 5-day forecast of **desert dust optical depth** and AOD@550 nm | https://ads.atmosphere.copernicus.eu — free, **account + API key** | The real input behind "clean before or after the dust storm". Replaces the simulator's synthetic `dust_aod`. |
| **ERA5 / ERA5-Land** | hourly reanalysis, 1950→present, wind at 100 m, irradiance components | https://cds.climate.copernicus.eu — free, **account + API key** | Long-term climatology; consistent weather features across years |

**ROLE: environmental context / enrichment, future work.** In this build `SoilingEvidence`

The adapter boundary is designed so CAMS/Open-Meteo can replace that source without touching the
soiling model.

**Known limitations:** CAMS and ERA5 need an account and key, which breaks the "runs offline on a
laptop" property this project is built around; both are therefore out of scope for the 24 h
build and in scope for the roadmap. Open-Meteo is free but non-commercial and gives a dust
*proxy* (PM10), not dust optical depth.

**Status:** `credential required` (CAMS, ERA5, AERONET registration), `fetchable` (Open-Meteo).

### 4.10 PRONOSTIA + NASA IMS — research-only, and honestly so

| Field | Value |
|---|---|
| PRONOSTIA | IEEE PHM 2012 Data Challenge, FEMTO-ST — accelerated bearing run-to-failure, accelerometers at 25.6 kHz (published) |
| NASA IMS | NASA Prognostics Center of Excellence bearing run-to-failure, 20 kHz (published) |
| Licence | research use (published) |

**ROLE: research-only, for the RUL roadmap slide and the fault dictionary.**

**Why they are not in the pipeline, stated bluntly:** our telemetry is 10-minute *averaged*
SCADA. These datasets are 20–25.6 kHz vibration. That is four to five orders of magnitude of
cadence difference. Nothing learned from a 25.6 kHz bearing signature transfers to a
10-minute-mean `drivetrain_vibration_mms` channel, and any claim that it does would be
indefensible. They appear here only because a judge may ask "what about run-to-failure data?" —
the answer is that it exists, it is excellent, and it answers a different question than ours.

**Status:** `not downloaded`.

## 5. Tier summary

**Tier 0 — the spine (in use).**
`RAI physics simulator`. Trains every model, defines every split, produces every ground-truth
label. Everything reported in `artifacts/evaluation.json` comes from here.

**Tier 1 — validation targets (adapters committed, nothing downloaded yet).**
`CARE to Compare` (wind detection + CARE score), `Kaggle two-plant solar` (solar residuals,
Indian site), `Kelmarsh + Penmanshiel` (cross-farm, false-alarm rate), `NASA POWER`
(environmental realism — the only Tier 1 source that needs no credential).
These four are what turn this from a demo into a claim. None has been touched.

**Tier 2 — case memory and enrichment (post-hackathon).**
`EDP failure logbook` (real pre-failure trajectories for `HistoricalCase`),
`CAMS / ERA5 / AERONET / MERRA-2` (dust and weather realism).

**Tier 3 — future work / research-only.**
`NREL PVDAQ`, `DKASC`, `SDWPF`, `PRONOSTIA`, `NASA IMS`, plus NSRDB, WIND Toolkit and the NREL
Gearbox Reliability Collaborative. Cited for method grounding; not loaded, not claimed.

## 6. The limitation that outranks all others

**Synthetic data cannot substitute for real-fleet validation.** Every number this system
produces — detection lead time, false-alarm rate, equipment-vs-environment accuracy, risk
calibration — is measured against faults we injected ourselves into telemetry we generated
ourselves, using physics assumptions shared by the generator and the detector. The correct
reading of a strong synthetic result is *"the pipeline is internally consistent and the
evaluation harness works"*, not *"this detects gearbox failures"*.

The remaining limitations, ranked:

2. No real fault labels have been seen by any model in this repository.
3. The test window is ~12.4 asset-months (derived), so the false-alarm rate has a Poisson
   standard error of roughly ±0.28 alarms/asset-month at a rate of 1.0 — a difference between
   0.6 and 1.0 is not resolvable with this much data.
4. Fault diversity is twelve scripted profiles against a real long tail.
5. Peer structure and wake behaviour are proxies (no turbine coordinates exist in the frozen
   fleet registry — measured from `rai/config.py`).
6. Licence diligence is incomplete: the CARE licence (CC-BY-SA-4.0) is share-alike and the
   Kaggle solar dataset has no explicit open licence in our records. Neither has been verified
   on the source page, and no redistribution of any derived dataset should happen until they are.

### The falsifiable next step

The first post-hackathon milestone is deliberately a test this project could fail:

> Run the **frozen** detector — same thresholds, no retuning — over CARE farm A, and report the
> CARE score with its four components. The published reference points are Isolation Forest 0.14,
> random 0.50, autoencoder 0.66. A result near 0.5 means the synthetic tuning did not transfer,
> and we will report that number as readily as a good one.

Until that run exists, this document's Tier 1 column is a plan.
